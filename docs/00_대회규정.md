## 1. 결과기 규정

### 반드시 지킬 것

- `answer_question(question: str)` 함수명과 입력 형식 유지
- 반환값에 `answer`와 `retrieved` 포함, `retrieved`는 관련도 순 1~4개
- 전역 FastAPI `app`, `GET /health`, `POST /answer` 제공
- 생성형 LLM은 **Qwen2.5-Instruct 계열**
- 새 Colab T4 런타임에서 위에서 아래로 한 번 실행되면 끝나는 자기완결형 파일
- **1번 셀 팀 구현 + 2번 셀 공통 러너**의 두 셀 구성
- 문항 수를 코드에 고정하지 않기 — 같은 제출본으로 공개 10문항과 비공개 30문항을 모두 처리
- 답변 JSON은 공통 러너가 만든다. 직접 조립하거나 수정하지 않는다

### 자유롭게 정할 것

1번 셀 내부 구현과 코드 구성, 패키지 설치, Qwen2.5-Instruct 계열 안에서의 모델 크기·미세조정·
양자화·생성 설정, 프롬프트와 RAG 구성, FastAPI 서빙 방식, 약관 원문 확보·가공 방법.

### 쓸 수 없는 것

- Google Drive 마운트, 미리 업로드해 둔 파일, 개인 PC 경로에 의존하는 코드
- 외부 생성형 LLM API, 원격 임베딩·리랭커, 원격 관리형 검색 서비스
- 실행 중 사람 입력을 기다리는 코드(`input()` 등)
- `torch` 재설치, `torch.compile`
- 질문과 상관없이 약관 전문을 매 질문 프롬프트에 통째로 넣는 방식
- 공통 러너의 문항·측정·저장 로직 수정

> 운영진은 팀 파일이 하나도 없는 새 세션에서 코랩을 실행한다. 드라이브에 올려 둔 파일에
> 의존하면 그 세션에서 전부 실패한다.

### 셀 구성 (1일차 오후 추가 안내)

"1번 셀은 자유롭게 구현 가능"은 **1번 셀 내부**의 구현 방법이 자유롭다는 뜻이다. 별도 코드 셀을
추가해도 된다는 의미가 아니다. 최종 제출본은 운영진이 제공한 두 셀 구성을 유지하고, 개발 중
쓴 시험용 셀은 1번 셀에 합치고 제거한다. 2번 셀은 `_SP_TEAM`에 팀 번호만 넣는다.

### 출제 기준 약관 4종

| 약관 | 시행일 |
|---|---|
| 카카오계정 약관 | 2026-05-29 |
| 카카오 위치정보 이용약관 | 2026-07-16 |
| 카카오 통합서비스약관 | 2026-05-29 |
| 카카오 통합 약관 | 2022-08-25 (종료된 아카이브 문서) |

약관 원문 파일은 배포하지 않았다. 현행 3종의 원문 확보 방법은 규정 내에서 자유이고,
통합 약관만 모든 팀이 동일 시행본을 쓰도록 공식 아카이브 링크를 제공했다.
`retrieved`의 문서명은 위 네 명칭을 그대로 쓴다.

### 공개 10문항의 위치

공개 10문항은 **연습 자료이고 예선 점수에 들어가지 않는다.** 예선은 2일차 제출본을 운영진이
비공개 30문항으로 실행·채점한 총점으로 정한다. 문항 수나 번호(P01~P10)를 코드에 적어 두면
비공개 30문항에서 실패한다.

### 예선 채점 기준

```
총점 = MRR 20점 + 핵심 내용 F1 30점 + 통합 LLM 평가 50점
```

- **MRR 20점** — 정답 근거가 1번째 1점, 2번째 0.5점, 3번째 약 0.33점, 4번째 0.25점, 4개 안에
  없으면 0점
- **핵심 내용 F1 30점** — 정답 핵심 내용과 팀 답변의 내용 토큰을 비교해 정밀도·재현율 균형 평가
- **통합 LLM 평가 50점** — Gemini Flash와 Pro가 평가. 내부 비중은 정확성 40% · 근거성 25% ·
  완결성 20% · 명료성 15%

HTTP 성공률·처리량·응답 시간은 기록만 하고 예선 점수에 반영하지 않는다.

### 제출

2일차 13:00 접수 시작, **13:30 마감**, Google Form 파일 업로드. 응답 1회만 가능.

- `result_generator_<팀>.ipynb` — 실제 실행한 두 셀짜리 코랩
- `answers_public_<팀>.json` — 같은 실행에서 나온 공개 답변 파일

Colab 공유 링크와 GitHub 저장소는 제출본으로 인정하지 않는다. 필수 파일 누락, 형식 검사
불통과, 구현·출력 형식 문제로 정상 채점할 수 없으면 **예선 0점**이다.

### 연습 채점

오프라인 질의응답 시간에 답변 파일을 올리면 운영진이 연습 평가기를 돌려 총점·MRR·키팩트 F1·
문항별 점수·판정 근거를 전달했다. 처음 팀당 2회였다가 **최대 6회로 확대**됐다.
연습 채점은 공개 10문항 + 평가 모델 1개, 실제 예선은 비공개 30문항 + 모델 2개(Flash·Pro)라
같은 결과기라도 점수가 달라진다.

## 2. 학생 평가기 규정

2일차 오후부터 제작. 문항·정답 기준·팀별 답변 파일을 입력받아 0~100점을 매기는 프로그램이다.

### 고정 조건

- 판정에는 **Gemini 3.5 Flash만** 사용
- 문항 수·문항 번호·질문 내용을 코드에 고정하지 않고 동적으로 처리
- **API 키를 노트북 코드에 직접 적지 않는다**
- 참가팀은 순위를 직접 매기지 않는다. 후보별 점수만 저장하고 순위는 운영진이 계산한다

평가 논리, 프롬프트, 점수 계산 방식, 코드 구조는 모두 자유. 예시 코드는 배포하지 않았다.

### 출력 형식 `eval_<팀>.json`

최상위에는 `results`만 둔다.

- `blind_id` — `BLIND01`~`BLIND05`를 그대로 기록
- `total` — 반올림하지 않은 0~100 원점수. 순위나 20점 환산점수를 넣지 않는다
- `status` — 전 문항 정상이면 `completed`, 일부 실패했지만 점수를 냈으면 `partial`,
  점수를 못 냈으면 `failed` (이때 `total`은 `null`)
- `rank`와 `schema_version`은 저장하지 않는다

다섯 후보가 모두 `completed`인 파일만 순위 산정에 쓴다. 중복·누락·`partial`·`failed`가
하나라도 있으면 **파일 전체가 제외**된다.

### 골드셋 공통 필드

평가기는 아래 필드를 읽고 처리할 수 있어야 하며, 비공개 골드셋의 추가 필드에 의존하면 안 된다.

- `questions[].id` — 답변 파일의 `qid`와 연결되는 식별자
- `questions[].question` — 평가 대상 질문
- `questions[].gold_articles` — 정답 근거 조항 목록 (`doc`, `article`, `citation`)
- `questions[].key_facts` — 답변에 포함되어야 할 핵심 내용 목록

### API 예산

팀당 공용 Gemini API 키 1개, 한도 **19,800원**. 3일차 교차 평가는 5팀 × 30문항 = 150회를
순차 실행하므로 시작 전 잔액을 최소 3,000원 남긴다.

### 제출

3일차 **15:10 마감**. 처음에는 `eval_<팀>.json` 1개였으나, 결과값이 제출한 평가기의 계산·출력
방식으로 나왔는지 확인하기 위해 **평가기 코랩 파일(.ipynb)까지 2개**로 변경됐다.
제출폼은 1회만 가능하고 수정할 수 없다.

## 3. 익명 교차 평가 20점 산정

### 절차

1. 운영진이 전 팀 결과기에 동일한 비공개 30문항을 넣어 답변 파일을 만든다
2. 운영진 평가기로 채점해 예선 순위를 정하고, 상위 5팀이 본선에 간다
3. 본선 5팀 답변에서 팀 정보를 지우고 `BLIND01`~`BLIND05`를 부여해 3일차 13:00에 전체 팀에 배포
4. **전체 참가팀**이 자기 학생 평가기로 다섯 후보를 모두 채점해 `eval_<팀>.json` 하나로 저장

### 점수 환산

평가 파일마다 다섯 후보의 `total`을 내림차순 정렬해 순위 점수를 준다.

| 파일 내 순위 | 1위 | 2위 | 3위 | 4위 | 5위 |
|---|---|---|---|---|---|
| 순위 점수 | 4점 | 3점 | 2점 | 1점 | 0점 |

팀마다 평가 기준과 원점수 분포가 달라 **원점수를 팀 간에 직접 평균 내지 않는다.** 각 파일 안에서
순위를 계산한 뒤 후보별 순위 점수를 정상 파일 전체에서 합산한다. 동점이면 공동 순위가 차지한
순위 점수의 평균을 적용한다.

누적 순위 점수가 높은 순서로 최종 순위를 정하고 환산한다.

| 최종 순위 | 1위 | 2위 | 3위 | 4위 | 5위 |
|---|---|---|---|---|---|
| 교차 평가 점수 | 20점 | 15점 | 10점 | 5점 | 1점 |

누적 순위 점수가 0점인 후보는 교차 평가 점수도 0점이다.

익명 답변에서 실제 팀을 추측하거나 결과 파일에 팀명을 적으면 안 된다. 14:30에 본선 진출팀이
공개된 뒤에도 `blind_id`는 `BLIND01`~`BLIND05`를 그대로 유지한다.

## 4. 발표 평가 (50점)

팀당 발표 5분, 질의응답 2분. 다섯 항목 각 10점.

1. 개선 목표와 접근 방향
2. 개선 과정과 기술적 선택
3. 실험 설계와 근거
4. 품질과 속도의 균형에 대한 판단
5. 실패와 한계, 추가 개선 방향

발표자료의 '핵심 기술·실험·판단'은 결과기에 한정되지 않는다. 평가기를 어떤 기준으로 설계했고
실제 평가에서 무엇을 확인했는지도 함께 담도록 안내됐다. 개발 과정을 모두 나열하기보다
최종 선택에 영향을 준 핵심 실험과 판단을 중심으로 설명하도록 요구됐다.
