## 1. 발표에서 전달할 핵심 메시지

**이 대회의 핵심은 약관을 검색하는 것에서 끝나지 않는다. 검색된 조항에서 질문에 필요한 원문 문장을 빠짐없이 선택하고, 불필요한 문장은 줄여 정확한 답변과 근거를 반환하는 것이 핵심이다.**

팀 9는 다음 방향으로 결과기를 개선했다.

1. 출제 기준 약관 4종을 고정하고 조항 단위로 검색
2. BM25와 로컬 임베딩을 결합해 관련 조항을 top-4에 배치
3. Qwen2.5-Instruct로 답변을 생성하되 원문 표현과 핵심 내용 보존
4. 모델 크기·양자화·프롬프트·후보 선택을 Colab T4에서 비교
5. 공개 점수와 자체 검증 결과를 분리해 최종 후보를 선택

## 3. 슬라이드별 발표 내용

### Slide 1. 문제 정의와 개선 목표

#### 문제

출제 기준일의 카카오 약관 4종에 대해 사용자의 질문에 답하고, 답변의 근거가 되는 문서명·조번호를 함께 반환하는 결과기를 만들어야 했다.

#### 결과기가 지켜야 한 계약

- `answer_question(question: str)` 함수 유지
- `answer`와 `retrieved` 반환
- `retrieved`는 관련 근거 1~4개
- 근거 형식은 `[문서명, 조번호]`
- 전역 FastAPI `app`, `GET /health`, `POST /answer` 제공
- 새 Colab T4에서 외부 파일 없이 처음부터 끝까지 실행
- 공통 러너인 2번 셀은 `_SP_TEAM` 외에 수정하지 않음

#### 개선 목표

| 목표 | 해결하려는 문제 |
|---|---|
| 검색 신뢰성 | 질문 표현이 달라도 정답 조항을 top-4 안에 넣기 |
| 답변 완결성 | 복합 질문의 하위 질문과 열거 항목을 빠뜨리지 않기 |
| 원문 충실도 | 숫자·기간·고유명사·법률 표현을 임의로 바꾸지 않기 |
| 실행 안정성 | T4에서 OOM·외국어 출력·타임아웃 없이 실행하기 |

#### 발표용 문장

> 처음에는 “정답 조항을 잘 찾으면 된다”고 생각했지만, 실험 결과 검색이 맞아도 답변에서 핵심 문장이 빠지면 F1과 LLM 평가가 떨어졌습니다. 그래서 검색과 생성을 별도의 개선 대상으로 나누었습니다.

### Slide 2. 대회 조건과 평가 기준

| 평가 항목 | 배점 | 결과기에서 영향을 받는 부분 |
|---|---:|---|
| 근거 문서·조항 순위(MRR) | 20 | `retrieved`의 정답 문서·조항 순위 |
| 핵심 내용 F1 | 30 | 답변에 정답 핵심 내용이 얼마나 포함되는가 |
| 통합 LLM 평가 | 50 | 정확성 40%, 근거성 25%, 완결성 20%, 명료성 15% |

HTTP 성공률·처리량·응답 시간은 기록되지만 예선 점수에는 직접 반영되지 않았다. 따라서 결과기 선택 기준은 다음처럼 정했다.

1. 형식 위반·실행 실패·OOM·타임아웃이 없는 후보를 먼저 남긴다.
2. 그 후보 안에서 MRR과 답변 품질을 우선한다.
3. HTTP 속도는 점수를 위해 극대화하기보다 T4에서 안정적으로 동작하는지 확인한다.

### Slide 3. 초기 문제 발견: 공개 검색 포화

공개 10문항에서 BM25·Dense·하이브리드 검색 모두 정답 조항을 top-4에 넣어 MRR 1.0을 기록했다.

하지만 공개 질문이 약관 원문과 어휘적으로 많이 겹쳐 있어, 공개셋만으로는 검색 알고리즘의 일반화 성능을 구분하기 어려웠다.

#### 대응

- 72개 조항 전체를 덮는 자체 검증 문항 구축
- basic·exact·trap·cross 유형으로 질문 다양화
- 질문과 정답 조항의 직접적인 문장 겹침을 줄이는 anti-leak 검사
- 공개셋 점수와 자체 검증셋 점수를 별도로 기록

#### 핵심 판단

> 공개 MRR 1.0은 “검색이 완성되었다”는 뜻이 아니라, 공개셋에서는 검색 차이가 드러나지 않는다는 뜻일 수 있었습니다.

### Slide 4. 최종 결과기 구조

```text
출제 기준 약관 4종 내장
        ↓
시행일 검증·정제
        ↓
문서명 + 조번호 + 조제목 기준 72개 조항 청크
        ↓
BM25 검색 ─┐
           ├─ 질문별 확신도 기반 가중치 + RRF
Dense 검색 ┘
        ↓
관련 조항 top-4
        ↓
Qwen2.5-7B-Instruct 4bit
        ↓
그리디·샘플링 후보 생성
        ↓
원문 복사율·외국어·잘림·반복 검사
        ↓
answer + retrieved 반환
```

#### 설계 선택

| 선택 | 이유 |
|---|---|
| 약관 전문 내장 | 새 Colab에서 개인 PC·Drive·네트워크에 의존하지 않기 위해 |
| 조항 단위 청킹 | `retrieved` 조번호 계약과 P03 같은 조항 내 열거 질문을 함께 만족하기 위해 |
| top-4 검색 | 근거 반환 계약을 지키면서 생성 컨텍스트를 제한하기 위해 |
| Qwen2.5-Instruct | 대회에서 허용된 로컬 생성 모델 조건을 만족하기 위해 |
| 7B 4bit | 3B보다 복합 질문·긴 열거를 처리할 여지를 확보하면서 T4 메모리에 맞추기 위해 |
| Best-of-N | 같은 모델에서도 그리디 외 후보를 탐색하고 원문 충실도가 높은 답을 선택하기 위해 |

### Slide 5. Retrieval 실험과 선택

#### 초기 합성 벤치 결과

| 검색 방식 | 합성 144문항 recall@4 | 합성 MRR |
|---|---:|---:|
| BM25 단독 | 0.644 | 0.450 |
| Dense 단독 | **0.944** | **0.757** |
| RRF 1:1 | 0.808 | 0.639 |
| Dense 가중 RRF | 0.877 | 0.695 |

Dense 단독이 합성 벤치에서 가장 높았지만, BM25는 공개 원문형 질문과 표현이 정확히 겹치는 경우 강했다. 따라서 하나를 폐기하지 않고 BM25와 Dense를 함께 사용했다.

#### 토크나이저와 문서명 부스트

| 설정 | 검증 MRR |
|---|---:|
| 어절 | 0.7917 |
| 어절 + 음절 bigram | **0.8380** |
| 어절 + 조사 제거 | 0.8194 |
| 문서명 부스트 0.50 | **0.9074** |

조사 제거는 손해가 있어 버리고, 음절 bigram과 문서명 부스트를 유지했다. 문서명이 질문에 들어온 경우에만 가산점을 주고 다른 문서를 강제로 제외하지 않아 P02 같은 복합 질문을 보호했다.

#### 동적 가중치

질문마다 BM25와 Dense의 점수 분포가 다르므로 고정 1:1 가중치 대신 질문별 확신도를 계산했다.

```text
확신도 = (1위 점수 - 2~11위 점수의 중위값) / 1위 점수
w = 1.0 + 0.6 × 확신도
```

BM25 확신도가 0.5 이상인 문항의 BM25 MRR은 0.938, 0.5 미만 문항은 0.688이었다. 이 차이 때문에 질문별 동적 가중치가 고정 가중치보다 타당하다고 판단했다.

### Slide 6. 모델·프롬프트·생성 실험

#### 모델 비교

| 모델 | 자체 48문항 전체 soft F1 | exact | trap |
|---|---:|---:|---:|
| Qwen2.5-3B-Instruct | **0.498** | **0.644** | **0.420** |
| Qwen2.5-1.5B-Instruct | 0.428 | 0.557 | 0.266 |

첫 공개 10문항에서는 1.5B가 높게 보였지만, 자체 48문항에서는 3B가 exact·trap 질문에 더 강했다. 작은 공개셋의 단일 결과보다 유형별 자체 검증 결과를 우선했다.

이후 팀원 계열에서는 Qwen2.5-7B-Instruct 4bit를 시험했다. 7B는 복합 질문에 유리했지만, 초기에는 CUDA OOM·중국어 혼입·누락이 발생했다.

#### 프롬프트 변경 방향

초기 프롬프트의 “군더더기 없이 답하라”가 지나치게 강해 필요한 인접 문장까지 줄이는 문제가 있었다.

다음 규칙을 강화했다.

- 하위 질문과 열거 항목을 빠짐없이 답하기
- 원문 표현·숫자·기간·고유명사를 그대로 유지하기
- 예·아니오 질문은 방향을 먼저 밝히고 근거 문장을 이어 쓰기
- 질문의 잘못된 전제를 그대로 반복하지 않기
- 조항에 없는 내용을 추측하지 않기

#### 생성 전략

- 그리디 후보 1개 생성
- temperature 0.7 샘플링 후보 생성
- 검색 조항 내 원문 복사율 확인
- 외국어 혼입·반복·잘림 후보 탈락
- 샘플링 후보가 충분히 좋을 때만 그리디 후보 교체

#### 다른 팀 결과의 의미

팀 11은 97.455점, 팀 12 `(2)`는 100.000점을 기록했다. 두 결과에서는 정답 핵심 문장과 항목 설명을 거의 빠짐없이 원문에 가깝게 출력한 점이 확인됐다.

다만 해당 팀의 내부 노트북이 없어 캐시·템플릿·모델·프롬프트 중 무엇이 원인이었는지는 확정할 수 없다. 따라서 이 결과는 구현을 복제한 근거가 아니라 **원문 핵심 내용 재현이 높은 점수에 중요하다는 비교 근거**로 사용했다.

### Slide 8. 품질과 속도의 균형

#### 속도를 별도 최적화하지 않은 이유

HTTP 성공률·처리량·응답 시간은 기록되지만 예선 점수에는 직접 반영되지 않았다. 따라서 가장 빠른 모델보다 다음 조건을 우선했다.

1. 새 T4에서 실행되는가
2. OOM 없이 모든 문항을 처리하는가
3. 외국어·잘림·반복 없이 답하는가
4. MRR·핵심 F1·LLM 판정이 더 높은가

#### 실제 판단

7B 4bit는 3B보다 모델 로딩과 생성 부담이 크지만, 로딩 시간이 점수에 포함되지 않았고 답변 품질 개선 가능성이 있었다. 초기 OOM은 컨텍스트 상한, 임베딩 모델 CPU 이동, CUDA 캐시 정리로 대응했다.

반대로 속도를 더 줄이기 위해 조항을 과도하게 줄이거나 2단계 요약을 사용하면 답변 누락이 커졌다. 결국 **HTTP 속도를 무조건 낮추는 것보다, T4에서 안정적으로 끝나는 범위 안에서 품질 점수를 최대화하는 선택**을 했다.

#### 발표 시 주의할 점

공통 러너의 HTTP 지표는 기록 대상이지만 별도 배점이 아니다. 발표에서는 “몇 초라서 우수하다”고 주장하기보다, “품질을 위해 7B와 후보 생성을 선택했지만 OOM·타임아웃을 막는 상한을 함께 두었다”고 설명한다.

#### 현재 한계

- 공개 10문항은 검색이 포화되어 비공개 일반화 성능을 보장하지 않는다.
- 팀 11·팀 12의 97~100점 구현을 직접 확인하지 못했다.
- 로컬 F1 프록시는 공식 LLM 50점을 계산하지 못한다.
- 답변 생성이 여전히 질문별 필요한 원문 span을 완벽하게 선택하지 못한다.
- 최종 제출본의 비공개 30문항 공식 점수는 확인되지 않았다.

#### 추가 개선 방향

1. 질문을 `예/아니오`, `열거`, `기간·숫자`, `복합 조건`, `전제 반박` 유형으로 먼저 분류한다.
2. 유형별로 필요한 원문 문장 후보를 선택한 뒤 중복과 무관 문장을 제거한다.
3. 생성 답변과 원문 span의 핵심 토큰·숫자·고유명사 일치 검사를 강화한다.
4. 자체 평가기와 공식 채점 결과의 차이를 계속 보정한다.
5. HTTP p50·p95·성공률과 품질 점수를 후보별로 같은 표에 기록해 선택 근거를 남긴다.
