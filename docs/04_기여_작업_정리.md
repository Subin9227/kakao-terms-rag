# 사용자 기여 작업 정리 — 카카오 약관 AI 성능 개선 대회

## 사용자 작업 타임라인

아래 표는 구현 코드를 작성한 작업을 제외하고, 사용자가 직접 요청·실행·검증·비교·결정한 일만 시간순으로 정리한 것이다.

| 순서 | 사용자가 직접 한 일 | 결과 또는 다음 단계 |
|---:|---|---|
| 1 | 대회 규정과 결과기 계약 전달: 2셀 구조, `answer_question`, `retrieved`, Qwen2.5-Instruct, 새 T4 조건 확인 | 개발 범위와 제출 제약 고정 |
| 2 | 카카오 약관 4종의 기준 시행일 확인 및 잘못 들어간 약관 날짜 수정·전달 | 원문 버전 기준 확정 |
| 3 | 약관을 문서명·조번호 기준의 검색 단위로 나누도록 요청 | 조항 단위 Retrieval 방향 확정 |
| 4 | 결과기 노트북을 Colab에 업로드·실행하고 `subprocess` 누락 오류 전달 | 런타임 오류 발견 및 수정 실행으로 연결 |
| 5 | 수정된 노트북을 다시 실행하고 공개 답변 JSON·`retrieved` 형식 확인 | 실제 T4 결과와 제출 형식 검증 |
| 6 | 3B·7B·4bit 모델, 법률 문서형 프롬프트, 추출식·하이브리드 실험 요청 | 모델별 누락·중국어 출력·OOM 문제 비교 |
| 7 | 평가 셀을 임시로 넣어 공개·H 문항의 F1·MRR·누락·지연 확인 | 검색 병목과 답변 생성 병목 분리 |
| 8 | 여러 팀의 답변 JSON과 공식 연습 채점 결과 수집 | 팀 9 후보와 객관적인 비교 기준 확보 |
| 9 | Hybrid·팀원·Best-of-N·추출식 후보를 비교하고 다음 실험 방향 결정 | Hybrid(2) 89.054, 팀원 2차 91.035 등 후보 평가 |
| 10 | 제출본·Colab·평가 자료를 한 폴더에 모으고 전체 흐름 정리 요청 | 최종 문서화와 사용자 기여 분리 |

## 사용자가 하지 않은 작업

아래는 프로젝트에 포함되었지만 사용자가 직접 작성한 것으로 분류하지 않은 작업이다. 구현 주체가 자료에서 확정되지 않는 경우에는 `자료상 구현자`로 표시했다.

| 작업 | 사용자 기여와 구분되는 실제 작업 | 주체 또는 근거 |
|---|---|---|
| 약관 처리 구현 | 약관 원문 다운로드·HTML/PDF 정제·조항 파싱·72개 청크 생성 코드 작성 | 팀원·Claude·Codex 결과기 자료 |
| Retrieval 구현 | BM25, dense 임베딩, RRF, 문서명 부스트, 동적 가중치 구현 | 팀원·Claude·Codex 결과기 자료 |
| 모델·서빙 구현 | Qwen 로딩·4bit 양자화·생성 설정·FastAPI `/health`·`/answer` 구현 | 결과기 노트북 자료 |
| 프롬프트·후보 선택 구현 | 시스템 프롬프트, 원문 복사율, 언어·잘림·반복 검사, Best-of-N 코드 작성 | 팀원 및 팀 결과기 자료 |
| 평가 도구 구현 | `message_linda`, `evaluation_cell_final`, `v2` 로컬 평가·키팩트 F1 추정기 작성 | 평가 셀·`ai-test-codex/v2` 자료 |
| 노트북 조립 | 구현 코드를 기본 틀의 1번 셀에 통합하고 제출용 2셀 구조로 조립 | 팀원·Claude·Codex 작업 자료 |
| 다른 팀 결과의 내부 구현 | 팀 11·팀 12가 사용한 모델·프롬프트·캐시·청킹 방식 작성 | 노트북 부재로 `[미확인]` |
| 종합 문서 작성 | 폴더 자료와 대화를 합쳐 개발 과정·역할·점수를 Markdown으로 정리 | Claude·Codex 문서화 작업 |

따라서 위의 첫 번째 표는 사용자의 기여만, 두 번째 표는 사용자가 수행하지 않은 구현·분석·문서화 작업만 담고 있다.

## 1. 문서 범위

이 문서는 ``에 모은 Codex·Claude 대화, Colab 실행 기록, 결과 JSON, 팀원 결과기와 채점 자료를 대조해 **사용자가 직접 수행하거나 결정한 일만** 정리한 기록이다.

표기 기준은 다음과 같다.

- `[대화 확인]` — 대화 원문에서 사용자의 요청·질문·결정을 확인할 수 있는 항목
- `[실행 결과]` — 사용자가 실제로 실행하고 경로·오류·출력을 전달한 항목
- `[사용자 전달]` — 현재 대화에서 사용자가 추가로 알려 준 사실. 파일·대화 원문에 직접 남은 근거와 구분
- `[판단]` — 위 자료를 바탕으로 정리한 해석
- `[미확인]` — 구현자나 공식 결과가 없어 확정할 수 없는 항목

## 2. 사용자의 역할 한 줄 요약

사용자는 결과기 핵심 코드를 전부 직접 작성한 개발자라기보다 **문제·규정의 기준을 고정하고, 원문 버전을 검증하고, Colab 실험을 실행하며, 평가 자료를 수집·비교하고, 다음 실험과 제출 후보를 결정한 실험 운영자·품질 검증자**였다.

## 4. 단계별 작업 흐름

### 4.1 대회 문제와 규정 고정

사용자는 먼저 대회 안내와 기본 틀 사용법을 전달하고, 결과기가 다음 계약을 지켜야 한다는 점을 작업의 전제로 삼았다. `[대화 확인]`

- `answer_question(question: str)` 함수명과 입력 형식 유지
- 반환값에 `answer`와 `retrieved` 포함
- `retrieved`는 관련 조항 1~4개이며 `[문서명, 조번호]` 형식
- 전역 FastAPI `app`, `GET /health`, `POST /answer` 제공
- 생성형 모델은 Qwen2.5-Instruct 계열
- 새 Colab T4에서 처음부터 끝까지 실행
- 2번 공통 러너는 `_SP_TEAM` 한 줄 외에 수정하지 않음
- Drive·개인 PC 경로·외부 생성형 API·원격 검색을 사용하지 않음
- `torch` 재설치와 `torch.compile`을 사용하지 않음

이 기준을 먼저 고정한 이유는 품질 개선 과정에서 규정 위반 구현이나 제출 형식 오류가 생기면 모델·검색 성능과 무관하게 채점이 불가능해질 수 있기 때문이다. `[판단]`

### 4.2 약관 원문과 시행일 검증

사용자는 카카오 약관 4종을 확보하고 결과기 코퍼스로 준비하는 작업을 요청했다. 기준 문서는 다음과 같았다. `[대화 확인]`

| 문서 | 기준 시행일 |
|---|---|
| 카카오계정 약관 | 2026-05-29 |
| 카카오 위치정보 이용약관 | 2026-07-16 |
| 카카오 통합서비스약관 | 2026-05-29 |
| 카카오 통합 약관 | 2022-08-25 아카이브 |

또한 사용자는 자료에 잘못 들어가 있던 약관의 시행일을 발견해 올바른 날짜로 수정·전달했다고 추가로 확인했다. 이 항목은 현재 대화에서 사용자가 직접 알려 준 사실이므로 `[사용자 전달]`로 기록한다.

이 검증이 필요했던 이유는 2024년 계정 약관처럼 다른 시행본을 사용하면 조항 문장과 정답 핵심 내용이 달라질 수 있기 때문이다. 이후 원문은 시행일을 기준으로 고정하고, 문서명과 조번호를 결과기의 근거 형식에 맞추는 방향으로 진행됐다. `[판단]`

### 4.3 조항 단위 분할 요청

사용자는 기본 틀과 공개 10문항을 참고해 약관을 문서명·조번호 기준으로 나누고 검색 가능한 단위로 분할하도록 요청했다. `[대화 확인]`

조항 단위로 나누도록 한 이유는 `retrieved`가 문서명·조번호를 요구하고, 한 조 안의 여러 항목 설명이 질문의 답이 될 수 있기 때문이다. 특히 P03처럼 한 조 안의 5개 서비스 설명을 묻는 문항은 너무 작게 나누면 일부 항목이 빠질 위험이 있다. `[판단]`

### 4.4 첫 Colab 실행과 오류 보고

사용자는 `result_generator_retrieval_t4.ipynb`를 Colab에 올려 1번 셀을 실행했고, 다음 오류를 전달했다. `[실행 결과]`

```text
NameError: name 'subprocess' is not defined
```

이 오류를 통해 런타임에 필요한 import가 1번 셀 안에 모두 있어야 한다는 점을 확인했고, 수정된 노트북을 다시 실행하는 단계로 넘어갔다. `[판단]`

이후 사용자는 수정 노트북의 공개 답변 JSON이 생성되었음을 알리고, JSON 형식과 제출 전 확인 방법을 점검했다. 이때 결과기 실행과 공통 러너의 역할을 구분하고, 답변 JSON을 직접 조립하지 않아야 한다는 조건도 계속 확인했다. `[대화 확인]`

### 4.5 모델 크기와 양자화 실험 결정

사용자는 3B 계열 결과기에서 7B 4bit 양자화 결과기를 별도로 시험해 보자고 결정했다. 로딩 시간과 HTTP 지표가 예선 점수에 직접 반영되지 않고, 7B가 복합 질문·열거형 질문에서 유리할 가능성이 있다는 판단 때문이었다. `[대화 확인]`

실험 중에는 다음 문제를 결과로 확인하고 다음 수정을 요청했다.

- 7B에서 중국어·한자 혼입
- 일부 답변의 설명·항목 누락
- 긴 컨텍스트에서 OOM 위험
- 생성 품질은 모델 크기만으로 자동 개선되지 않음

사용자는 팀원이 만든 법률 문서형 프롬프트를 제공하고 3B와 7B 모두에 적용해 비교하도록 했다. 프롬프트 적용의 목표는 원문 표현 보존, 복합 질문의 하위 항목 완결, 숫자·기간·조문 번호 보존, 전제 반박, 예·아니오 방향 보정이었다. `[대화 확인]`

### 4.6 평가 셀 실행과 정량 비교

사용자는 `message.txt`, `message_linda.txt`, `evaluation_cell_final.txt` 계열의 평가 셀을 결과기에 임시로 넣어 실행했다. 공개 10문항과 자체 H 문항의 문항별 F1 프록시·MRR·지연·누락 내용을 직접 전달했다. `[실행 결과]`

평가 셀을 사용한 목적은 다음과 같았다.

1. `gold_questions_public10.json`의 공식 공개 문항에 대한 답변 누락 확인
2. `retrieved`의 정답 조항 포함과 순위 확인
3. P02·P07·P08·P09·P10처럼 검색은 맞지만 답변이 불완전한 문항 분리
4. H 문항으로 공개 10문항에만 맞춘 과적합 여부 확인
5. 최종 제출 전 평가 셀을 제거해야 한다는 제출 구조 재확인

이 과정에서 사용자는 평가 문항의 기준은 `gold_questions_public10.json`이고, 다른 JSON 결과를 평가 문항 데이터로 그대로 재사용하면 안 된다는 점도 확인했다. `[대화 확인]`

사용자는 다음 팀의 공개 답변·채점 자료를 가져와 비교 대상으로 제공했다. `[대화 확인]`

### 4.8 실험 방향 전환과 후보 선택

사용자는 결과가 좋아졌다가 다시 떨어지는 현상을 확인하고, 하이브리드 RAG 주변만 탐색하지 말고 동적 맥락·캐시·원문 복사·Best-of-N 등 다른 시작점을 검토하도록 방향을 전환했다. `[대화 확인]`

실제로 요청·검토한 실험 방향은 다음과 같다.

- BM25와 dense 임베딩을 결합한 하이브리드 검색
- 문서명 부스트와 동적 가중치
- Qwen2.5 3B와 7B 4bit 비교
- 법률 문서형 시스템 프롬프트
- 추출식 답변과 생성식 답변 비교
- 그리디 후보와 temperature 0.7 샘플링 후보의 Best-of-N
- 원문 복사율·외국어 혼입·잘림·반복을 이용한 후보 선택
- 공개 문항 캐시나 정답 문장 재현 전략의 가능성 검토

이 중 팀원 2차 계열은 공개 공식 점수 91.035로 확인되었고, Hybrid(2) 계열의 89.054보다 높았다. 반대로 추출식 결과기는 사용자 전달 기준 82.510으로 낮아져, 단순 추출이 항상 생성보다 낫지는 않다는 점도 확인했다. `[실행 결과]` `[사용자 전달]`
