# KTB RAG 예선 결과기 — 전체 의사결정 기록

카카오 약관 4종 RAG 결과기를 만들면서 내린 선택, 그 근거, 그리고 번복한 것들을 시간순으로 적는다.
숫자는 모두 실측값이고, 틀렸던 판단은 틀렸다고 적는다.

**최종 점수 흐름: 89.056 → 91.035 → 최종본**

---

## 0. 출발 개념 — 강의 노트에서 가져온 두 가지

### 극대(local)와 최대(global)

개선을 쌓다 보면 지표가 오르다 멈춘다. 그건 시작점 부근의 극대점이지 최선이 아니다.
이 프로젝트에서 두 번 겪었다.

- 공개 10문항 검색 MRR이 1.000에 도달 → 더 올릴 곳이 없어 보였지만, 어휘를 바꾼 질문에서는
  0.500으로 무너졌다
- 프롬프트를 열 번 넘게 고쳤지만 총점이 88~91 범위를 벗어나지 못했다

### 동적 맥락과 정적 모델

```
w1x1 + w2x2 + w3x3
```

모델 파라미터는 고정이다. 질문마다 달라지는 맥락에 대응할 수 있는 지점은 **검색 융합의
가중치**뿐이라는 인식이, 후반의 동적 가중치 구현으로 이어졌다.

## 1. 데이터 포맷 — DOCX/HTML 선택, PDF 배제

**선택**: DOCX와 HTML을 우선, PDF는 최후 수단.

**근거**: DOCX·HTML은 제목·표·목록이 태그로 존재한다. PDF는 인쇄용 포맷이라 문단·제목 개념이
파일 안에 없고, 2단 편집에서 읽기 순서가 섞이며 머리말·꼬리말이 본문에 끼어든다.

실제로 통합약관 PDF에서 `8/10/26, 11:31 AM 이용약관` 같은 웹 인쇄 머리말이 조문 사이에
들어와 있었다.

**변환 후 검증 방식**: 원본에서 텍스트를 추출해 **공백·번호 마커·마크다운 문법을 제거한
문자열끼리 대조**했다. 눈으로 보지 않고 프로그램으로 확인한 것이 나중에 약관 개정을 발견하는
결정적 계기가 됐다.

| 문서 | 원본 | 유사도 | 차이 |
|---|---|---|---|
| 카카오계정 약관 | docx | 0.99934 | 최상단 제목 표기만 |
| 카카오 통합서비스약관 | docx | 0.99942 | 최상단 제목 표기만 |
| 카카오 통합 약관 | pdf | 0.98210 | 웹 목차·푸터만 |

## 2. 데이터 준비 — 런타임 크롤링 대신 코드 내장

**선택**: 약관 4종 전문을 셀 안에 문자열로 내장.

**근거 셋**

1. 운영진은 파일이 하나도 없는 새 세션에서 실행한다. 크롤링이 실패하면 재시도 기회가 없다
2. 문항당 120초 제한이 있는데 첫 문항에서 네트워크 재시도가 돌면 그것만으로 위험
3. 재현성. 실행마다 원본이 달라지면 지표 비교 자체가 무의미하다

**대조 사례**: 다른 팀은 런타임에 kakao.com을 크롤링했다. 접속 실패 시 전량 실패라는 구조적
위험을 안고 있었고, `pip install -U transformers`가 torch를 건드릴 소지도 있었다.

**검증을 코드에 심음**

```python
EXPECTED_ARTICLE_COUNTS = {"카카오계정 약관": 17, ...}
```

붙여넣기 실수가 있으면 채점 중이 아니라 셀 실행 시점에 즉시 터지게 했다. 조용히 망가지는
실패가 가장 나쁘다는 판단.

## 3. 청킹 — 계약이 설계를 강제했다

**선택**: 조(條) 단위. 긴 조항도 2차 분할하지 않음.

**근거**: `retrieved`가 `[문서명, 조번호]` 형식이라는 계약 때문에 조 단위가 필수였다. 슬라이딩
윈도우를 쓰면 청크가 어느 조에서 왔는지 되짚을 수 없다.

2차 분할을 포기한 이유는 "열거된 5가지를 각각 답하시오" 같은 문항에서 뒷부분이 잘리면 답이
반쪽이 되기 때문. 결과적으로 72개 조항(17/18/21/16).

청크 본문 앞에 `[문서명 제N조 (제목)]`을 붙였다. 검색 정확도와 인용 정확도가 함께 올라간다.

## 4. BM25 직접 구현 — 논쟁과 측정

**초기 선택**: 외부 패키지 없이 직접 구현.

**제기된 반론**: "패키지를 쓰는 게 답을 더 맞힐 확률이 높지 않나?"

**측정으로 답함**

| 설정 | 공개 10문항 recall | MRR |
|---|---|---|
| 직접 구현 (k1=1.2) | 1.000 | 1.000 |
| rank_bm25 공식 재현 (k1=1.5) | 1.000 | 1.000 |
| k1=0.9, b=0.4 | 1.000 | 1.000 |
| k1=2.0, b=0.9 | 1.000 | 1.000 |

파라미터를 어떻게 흔들어도 동일했고, 토크나이저를 공백 split으로 바꿔도 1.000이었다.
**공개 문항이 원문 표현을 그대로 쓰기 때문에 변별이 안 되는 것**이었다.

그래서 어휘를 바꾼 질문 8개를 만들어 다시 쟀다.

| 토크나이저 | 패러프레이즈 recall |
|---|---|
| 어절+조사제거+bigram | 0.500 |
| 어절만 | 0.500 |
| 공백 split | 0.500 |

**전부 0.500.** BM25는 어휘 일치 알고리즘이라 여기가 원리적 한계이고 구현으로는 못 넘는다.

**결론 유지**: 패키지 교체는 정확도와 무관하고 설치 실패 지점만 늘린다. 직접 구현 유지.

## 5. 판단 번복 ① — 임베딩은 필요했다

**초기 판단**: "BM25만으로 공개셋 만점이니 임베딩이 불필요할 수도 있다."

**번복**: 위 패러프레이즈 실험에서 BM25가 0.500으로 무너지는 것을 확인하고 철회했다. 본선
30문항은 표현이 다를 것이므로 밀집 검색이 실제로 일을 한다. `w_dense`를 낮추자던 제안도 함께
철회했다.

**교훈**: 공개셋에서 만점인 구성요소를 "불필요"라고 판단하면 안 된다. 공개셋이 그 요소를
시험하지 않았을 뿐일 수 있다.

## 7. few-shot 오염 사고 — 두 번의 교정

### 1차 사고: 제0조 누출

유도형 질문(P08)에 "아니오"로 답하게 하려고 예시를 넣었다.

```
<조항 1>
[예시 약관 제0조 (준칙)]     ← 문제
```

다음 실행에서 **전혀 무관한 P05의 답변 끝에 `근거는 제1조 제0조와...`가 붙었다.** `제0조`는
코퍼스 어디에도 없는 번호다.

**조치**: 예시에서 조문 번호를 완전히 제거.

### 2차 발견: few-shot 자체가 과적합이었다

"구체적인 예시를 들면 거기에 치우치지 않나"라는 지적을 받고 다시 보니, **few-shot 두 개가
사실상 P08과 P07을 그대로 베낀 것**이었다.

**조치**: 공개 문항과 무관한 가상 사례로 전면 교체.

| | 소재 | 시연하는 행동 |
|---|---|---|
| FS1 | 자료 보관기간 | 유도형 → `아니오` + 원문 그대로 + 이어지는 문장 |
| FS2 | 설비 점검 위탁 | 다항 질문 각각 + 주체 이름 그대로 + 예/아니오 없이 |

조 번호와 실제 회사명은 넣지 않았고, 평가 셀에 **예시값 누출 자동 감지**를 추가했다.

**교훈**: few-shot에 넣은 구체값은 모델이 복사한다. 실제 정답을 심으면 과적합, 가짜 값을 심으면
오염이다. 형식만 가르치고 값은 넣지 않아야 한다.

## 8. 자체 검증셋 구축 — 이 프로젝트의 전환점

**문제**: 공개 10문항은 점수에 반영되지 않는데, 개선 여부를 판단할 지표가 그것뿐이었다.

**선택**: 공개 문항이 건드리지 않은 **60개 조항**에서 H 세트 18문항을 직접 제작.

- 4개 문서 고른 분포 (5/5/4/4), 유형 basic 8 / exact 8 / trap 2
- 인증서비스, 유료서비스 환불, 청소년보호 등 새로운 주제
- **모든 키팩트가 해당 조문에 실재하는 문자열임을 프로그램으로 확인** (라벨 오류 0건)

**즉시 드러난 사실**

```
공개 10문항  BM25 MRR 1.000   ← 낙관적
검증 18문항  BM25 MRR 0.847   ← 현실적
```

이 격차를 몰랐다면 검색을 이미 끝난 문제로 착각했을 것이다.

## 9. 모델 선택 — 3B fp16 → 7B 4bit

### 초기 선택: 3B fp16

성능이 채점에 포함되는 줄 알았을 때의 판단. T4는 Turing 세대라 bitsandbytes NF4의 역양자화
커널이 느리고, 절약한 메모리 대역폭보다 오버헤드가 크다는 근거.

### 번복: 7B 4bit

**규정 확인 결과 성능 측정값이 예선 점수에 반영되지 않았다.** 지연을 아낄 이유가 사라졌고 남은
제약은 문항당 120초 타임아웃뿐. 7B로 전환.

### 7B 첫 실행 — 두 가지 치명적 실패

```
CUDA OOM      3문항  → 답변·retrieved 모두 비어 0점
중국어 혼입    3문항
H 검색 recall 0.778
H 키팩트      0.611
```

OOM은 프롬프트가 최대 12,000자까지 부풀어 어텐션에서 4GB를 한 번에 요구하면서 발생.
중국어는 **프롬프트에 "한국어로 답하라"는 지시가 아예 없었기 때문**. 3B에서는 한 번도 없던
현상이라 놓친 부분이었다.

### 대책 6종

| 대책 | 목적 |
|---|---|
| `MAX_CTX_CHARS` 3000 → 1800 → 2200 → 3600 | 조 하나당 상한 |
| `MAX_TOTAL_CTX` 신설 → 7200 | 조 4개 합계 상한 |
| 임베딩 모델을 인덱싱 후 CPU로 이동 | 약 1.2GB 확보 |
| `generate` 후 `empty_cache()` | 문항 간 누적 차단 |
| `PYTORCH_CUDA_ALLOC_CONF=expandable_segments` | 단편화 완화 |
| 언어 규칙 신설 | 중국어 방지 |

**결과: OOM 0건**, H recall 0.778 → 0.944, H 키팩트 0.611 → 0.861.

`MAX_CTX_CHARS`를 3600까지 올린 근거는 실측이다. 조항 길이 중앙 599자, 최대 3,564자,
top-4 합계 최대 7,080자였다. 3600/7200이면 어떤 조도 잘리지 않는다.

## 10. 채점 기준 역산 — 최적화 방향이 뒤집혔다

연습 채점 첫 결과.

```
총점 89.056
  MRR      20.000 / 20   ← 만점
  키팩트 F1 20.631 / 30   ← 9.4점 손실
  LLM 판정  48.425 / 50   ← 1.6점 손실
```

**판정은 이미 96.85로 거의 만점.** 짜낼 수 있는 건 1.6점뿐이고 F1에 9.4점이 걸려 있었다.

### F1이 낮은 이유는 재현율

문항별 `keyfact_recall` 평균 0.68. 14팀과 비교하면 원인이 분명했다.

| | 우리 | 14팀 |
|---|---|---|
| 키팩트 재현율 | 0.68 | **0.78** |
| 정밀도(역산) | ~0.70 | ~0.68 |
| F1 | 0.6877 | **0.7275** |
| LLM 판정 | **96.85** | 95.35 |

**정밀도는 비슷한데 재현율만 낮았다.** 답변을 짧게 만든 대가였고, 내가 "간결성"을 강조한 것이
직접적 원인이었다.

### 토큰 매칭이라는 사실

P05는 **LLM 판정 완결성 10/10 만점인데 keyfact_recall은 0.67**이었다.

```
원문:  위치정보시스템에 자동으로 기록·보존하며
답변:  위치정보시스템에 자동으로 기록되어
```

의미는 같지만 `기록·보존` 토큰이 없어 키팩트 하나를 놓쳤다. **원문을 그대로 베끼는 것이 곧
점수**라는 결론.

### 트레이드오프가 없다는 발견

LLM 판정의 감점도 전부 **완결성**에서 났다. F1이 놓친 키팩트와 판정이 감점한 키팩트가 동일.
즉 재현율을 올리면 둘 다 오른다. 시뮬레이션으로 안전 여유도 확인했다.

```
        정밀도 0.70   0.65   0.60   0.55
재현율 0.85    23.0   22.1   21.1   20.0
현재 20.63점 — 재현율 0.85 이상이면 정밀도 0.60까지 떨어져도 이득
```

**방향 전환**: "간결하게" → "원문 그대로, 답을 완성하는 문장까지".

이 수정으로 **89.056 → 91.035**. 오른 2점이 전부 F1(20.631 → 22.611)이었다.

## 11. 프롬프트 — 네 번의 구조 변경

### 1차: 압축 (1,488자 → 625자)

규칙 14개에 중복이 많았다. 6+7(원문 인용), 11+12+13(군더더기), 1+2(근거 한정)를 통합해 7개로.
**19개 기능이 모두 남아있는지 프로그램으로 대조**한 뒤 확정. 확보한 공간은 조항 예산으로 환원.

### 2차: 재배치 (위치가 중요하다)

언어모델은 프롬프트의 처음과 끝에 주의를 두고 가운데를 흘린다. F1을 좌우하는 규칙이 하필
가운데(0.35, 0.50)에 있었다. 점수 기여도 순으로 재배치하고 말미에 핵심을 재강조.

### 3차: 실패로부터의 되돌림 ← **번복**

2차에서 언어 규칙을 8번(위치 0.83)으로 내렸더니 **중국어가 다시 나왔다.** 직전 실행에서 0건이던
건 그때 언어 규칙이 1번이었기 때문. 내 판단 착오였다.

동시에 `주체·예의 이름을 그대로`가 가운데로 밀리면서 **P07에서 `㈜카카오모빌리티`가 사라졌다.**

**교훈**: 치명적 실패를 막는 규칙(언어)은 F1 규칙보다 앞에 둬야 한다. 한 문항을 통째로 잃는
것(-3.3점)이 F1 몇 %보다 크다.

### 4차: 구체 예시 배제 ← **번복**

`'기록·보존'을 '기록'으로 줄이지 마시오` 같은 구체어를 넣었다가 제거했다. "구체적인 예시를 들면
거기에 치우쳐서 다른 게 들어왔을 때 잘못 얘기할 가능성이 늘어난다"는 지적이 타당했다.

```
이전: '기록·보존'을 '기록'으로, '1인'을 '1명'으로 줄이지 않습니다
지금: 단어를 짧은 말로 바꾸거나, 나열된 말 중 일부를 빼거나,
      문장을 명사형으로 줄이지 않습니다. 조사와 어미까지 원문을 따릅니다.
```

프레이밍도 바꿨다. **`답변은 새로 쓰는 글이 아니라, 조항에서 필요한 문장을 골라 옮기는
작업입니다.`** 작문이 아니라 선택과 복사로 과제를 재정의하는 문장.

## 12. 동적 가중치 — 강의 개념의 구현

**문제**: 질문마다 두 검색기의 신뢰도가 다른데 코드는 1.0 : 1.0 고정이었다.

**선택**: 규칙 기반 대신 **확신도 기반**.

질문에 `제N조`가 있으면 BM25를 올리는 식의 규칙은, 내가 만든 규칙이 본선 문항의 표현을 맞힐지
보장할 수 없다. 대신 각 검색기가 점수 분포에서 스스로 확신도를 드러내게 했다.

```python
확신도 = (1위 점수 - 2~11위 중위값) / 1위 점수
w = 1.0 + 0.6 × 확신도
```

**유효성 확인**

| BM25 확신도 | 문항 수 | BM25 단독 MRR |
|---|---|---|
| ≥ 0.5 | 24 | 0.938 |
| < 0.5 | 4 | 0.688 |

확신도가 낮은 문항에서 실제로 못 맞힌다. 지표가 유효하다는 증거.

## 14. 후보 생성 — "색다른 시작점"

**문제 인식**: 프롬프트를 열 번 넘게 고쳤는데 88~91을 벗어나지 못했다. 강사님의 "완전 색다른
시작점"이라는 질문이 여기 걸렸다.

**깨달음**: 지금까지 `do_sample=False`, 즉 **그리디만 썼다.** 소프트맥스에서 가장 큰 값 하나만
집는 방식이라 프롬프트를 고쳐도 늘 같은 한 갈래 안에서 움직인 것이다.

```
소프트맥스  1위 0.7 / 2위 0.2 / 3위 0.1
가장 큰 것만 고르는 것 = 그리디
Temperature 가 랜덤 초이스를 해준다
```

**선택**: 온도를 올려 여러 후보를 뽑고, **조항 원문을 가장 충실히 옮긴 답을 고른다.**

```python
충실도 = 답변의 5글자 조각 중 조항 원문에 실재하는 비율
```

F1이 토큰 매칭이라 이 값이 곧 점수와 연결된다. 실측으로 검증했다.

```
P07  ㈜카카오모빌리티 유지 0.595  vs  누락 0.379
P09  원문 그대로 1.000        vs  바꿔 씀 0.696
```

### 선택 방식의 번복 ← **argmax → 조건부 교체**

처음엔 점수가 가장 높은 후보를 무조건 채택하는 구조였다. "그리디를 기본으로 두고 명확히 나을
때만 교체하는 게 낫지 않나"는 제안을 받아 바꿨다.

```python
best = 그리디 (검증된 기준선)
샘플링 후보는 충실도가 SWAP_MARGIN 이상 높고 어미도 나빠지지 않을 때만 교체
외국어·잘림·중복은 점수가 아니라 실격 조건으로 분리
```

**근거**: 점수 최고 후보를 무조건 채택하면 근소한 차이로 검증된 답을 잃을 수 있다. 그리고
길이·중복은 점수로 매기기 애매하지만 외국어·잘림은 명확한 실격 사유다.

**부수 효과**: 중국어 후보가 자동 탈락한다. 3개 중 하나만 한국어여도 그게 선택된다.

## 15. 조합 실험과 최종 선택

여러 조합을 채점기로 검증했다.

| 구성 | 결과 |
|---|---|
| 단일 생성 (후보 없음) | 89.056 |
| **후보 3개 · 온도 0.7** | **91.035** |
| 후보 2개 | ~89 (P07에서 ㈜카카오모빌리티 누락) |
| 후보 4개 · 온도 0.4 | ~89 (P07 악화, 시간 2배) |
| **후보 4개 · 온도 0.7 (최종)** | **P07 완전 커버** |

### 온도 0.4 실험의 실패 ← **가설 번복**

내 가설은 "낮은 온도 = 원문에 가까움"이었다. 실제로는 **그리디와 거의 같은 후보만 나와 교체가
일어나지 않았다.** 후보를 4개로 늘렸는데도 P07이 오히려 나빠졌다.

### 결정적 관찰

후보 3개(온도 0.7)와 후보 4개(온도 0.4) 결과를 비교하니 **9개 문항이 글자까지 동일**했다.
P07만 달랐다.

이유는 하나뿐이다. **그 9문항에서는 그리디가 채택됐다.** 샘플링 후보가 실격되거나 교체 기준을
못 넘긴 것. 그리디는 결정론적이라 시드·온도·후보 수와 무관하게 항상 같은 답을 낸다.

즉 **후보 생성이 실제로 작동한 문항은 P07 하나뿐**이었다.

### 최종본

`후보 4개 · 온도 0.7`에서 P07이 세 요소를 모두 냈다.

```
회사가 아닌 카카오 계열사에서 제공하는 서비스이며,
약관은 예로 ㈜카카오모빌리티가 제공하는 카카오 T 택시 서비스를 들고 있습니다.
```

나머지 9문항은 91.035와 동일. **p95도 111초 → 82초로 내려가** 타임아웃 마진이 넉넉해졌다.

## 19. 전체를 관통한 교훈

### 측정하지 않은 것은 모르는 것이다

BM25 패키지 논쟁, 임베딩 필요성, 프롬프트 규칙 위치, 온도 방향 — 전부 직관과 측정 결과가
달랐다. 특히 임베딩은 "불필요하다"고 판단했다가 측정으로 뒤집었다.

### 틀린 답의 재료가 입력에 있었는지 먼저 확인한다

모델이 틀렸을 때 청킹을 의심했지만, 확인해보니 필요한 문장이 청크 안에 전부 있었다. 여기서
갈리면 고칠 곳이 완전히 달라진다. 확인 없이 감으로 청킹을 만졌다면 멀쩡한 것을 망가뜨렸을
것이다.

### 공개셋 지표는 천장에 닿으면 정보를 잃는다

MRR 1.000은 "완벽하다"가 아니라 "이 지표로는 더 구분할 수 없다"는 뜻이다. 자체 검증셋을 만든
것이 가장 값어치 있는 투자였다.

### 채점 기준을 역산하면 우선순위가 바뀐다

배점을 알기 전에는 프롬프트와 모델을 만졌다. 알고 나니 F1 재현율 하나에 9.4점이 걸려 있었고,
그때까지 강조하던 "간결성"이 바로 그 점수를 깎고 있었다.

### 개선은 양방향으로 움직인다

프롬프트를 고칠 때마다 어떤 문항은 좋아지고 어떤 문항은 나빠졌다. P04를 잡으면 P07이 무너지는
식이었다. **매번 백업하고 나빠지면 되돌린다**는 규율이 없었다면 최고점을 잃었을 것이다.

### 안전한 실패와 치명적 실패를 구분한다

키팩트 하나 누락은 부분 점수 손실이지만, OOM·중국어·타임아웃은 문항을 통째로 잃는다(-3.3점).
후자를 막는 장치가 항상 우선이다.

### 극대점을 벗어나려면 축을 바꿔야 한다

프롬프트를 열 번 고쳐도 88~91을 벗어나지 못했다. 벗어난 계기는 **그리디라는 디코딩 방식 자체를
의심한 것**이었다. 같은 축에서의 개선은 결국 같은 지형 안에 머문다.
