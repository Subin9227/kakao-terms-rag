# 카카오 약관 RAG — 결과기와 평가기 (팀 9)

카카오테크 부트캠프 판교 4기 **부하테스트 & 성능개선 대회** (2026.08.10~08.12) 산출물입니다.
3일간 두 가지를 만들었습니다.

1. **결과기** — 카카오 약관 4종에 대한 질문에 근거 조항을 인용해 답하는 RAG 파이프라인.
   Colab T4 한 장에서 Qwen2.5-7B-Instruct(4bit)를 로컬로 돌립니다
2. **학생 평가기** — 다른 팀의 답변을 0~100점으로 채점하는 프로그램. 본선 5팀 익명 답변의
   교차 평가에 실제로 사용됐습니다

**결과: 우수상 — 전체 17팀 중 예선을 통과해 본선 5팀(3·9·10·12·13팀)에 올랐고,
본선에서 2위를 했습니다.**

## 대회 구조

```
예선   운영진이 전 팀 결과기에 비공개 30문항을 넣어 채점 → 상위 5팀 본선 진출
본선   발표 50점 + 예선 결과기 30점 + 전체 참가팀 익명 교차 평가 20점 = 100점
       → 최우수 1팀 · 우수 1팀 시상
```

본선 100점 중 50점이 발표, 30점이 예선 결과기 점수, 20점이 다른 팀들이 우리 답변을
자기네 평가기로 채점한 교차 평가입니다. 즉 **코드만 잘 만들어서는 절반도 못 채웁니다.**
이 저장소에 규정 원문과 판단 근거를 함께 둔 이유이기도 합니다.

팀별 세부 점수는 공개되지 않아, 세 항목 중 어디서 벌었는지는 알 수 없습니다.

규정 전문은 [`docs/00_대회규정.md`](docs/00_대회규정.md)에 정리했습니다.

# 1부. 결과기

## 채점 기준 (예선)

```
총점 = MRR 20점 + 핵심 내용 F1 30점 + 통합 LLM 평가 50점
```

LLM 평가 내부 비중은 정확성 40% · 근거성 25% · 완결성 20% · 명료성 15%이고,
Gemini Flash와 Pro 두 모델이 채점했습니다.

## 연습 채점 결과 (운영진 공개 10문항)

| 판본 | 총점 | MRR | 키팩트 F1 | LLM 판정 |
|---|---:|---:|---:|---:|
| [11번 — 코퍼스 내장](1-result-generator/experiments/11_약관코퍼스_코드내장_크롤링제거.ipynb) | 89.054 | 1.0000 | 0.7076 | 95.650 |
| [16번 — 베스트오브N (N=3)](1-result-generator/experiments/16_베스트오브N_도입_N3_샘플링.ipynb) | **91.035** | 1.0000 | **0.7537** | **96.850** |

MRR은 두 판본 모두 만점입니다. 오른 1.981점은 **전부 키팩트 F1**에서 나왔습니다
(0.7076 → 0.7537). 검색은 일찍 천장에 닿았고, 그 뒤의 개선은 전부 "검색된 조항에서
정답에 필요한 원문 문장을 빠짐없이 옮기는 일"이었습니다.

> 공개 10문항은 **연습 자료이고 예선 점수에 들어가지 않습니다**(규정 명시). 예선은 비공개
> 30문항으로 따로 채점했고, 팀별 점수는 공개되지 않았습니다. 위 표는 개발 중 방향을 잡는 데
> 쓴 지표이지 예선 성적이 아닙니다.

## 최종 구성

```
약관 4종 내장 (조 72개, 원본과 문자 단위 대조 완료)
   ↓
BM25(한국어 토크나이저, 직접 구현) + BGE-M3 임베딩(로컬, 인덱싱 후 CPU)
   ↓
확신도 기반 동적 가중치 → RRF 융합 → top-4
   ↓
Qwen2.5-7B-Instruct 4bit · 그리디 1 + 샘플링 3(온도 0.7)
   ↓
원문 충실도 기준 조건부 교체 (외국어·잘림·중복은 실격)
   ↓
{answer, retrieved 4개}
```

```python
USE_7B = True                # 7B 4bit
USE_DYNAMIC_WEIGHTS = True   # 확신도 기반 가중치
USE_BEST_OF_N = True
N_CANDIDATES = 4
SAMPLING_TEMPERATURE = 0.7
TOP_K = 4                    # P02 정답이 3개 문서에 걸침
MAX_NEW_TOKENS = 640         # P03(467자) 잘림 없음 확인
MAX_CTX_CHARS = 3600         # 최장 조 3,564자
MAX_TOTAL_CTX = 7200         # 실측 top-4 최대 7,080자
```

최종 검증: `n_errors 0 · timeout_qids [] · doc_violations 0 · env_warnings []` ·
p95 82.3초 (제한 120초)

약관 원문은 크롤링하지 않고 코드에 내장했습니다. "Google Drive 마운트·미리 업로드한 파일
금지" 규정 때문이기도 하지만, 운영진이 **팀 파일이 하나도 없는 새 세션**에서 실행한다는
조건이 결정적이었습니다.

# 2부. 학생 평가기

2일차 오후부터 만들었습니다. 3일차에 본선 5팀의 익명 답변(`BLIND01`~`BLIND05`)을 채점해
`eval_9.json`을 제출했고, 이 결과가 교차 평가 20점 산정에 실제로 반영됐습니다.

## 규정이 설계를 강제한 부분

| 규정 | 구현에 미친 영향 |
|---|---|
| Gemini 3.5 Flash **만** 사용 | `MODEL_ID = "gemini-3.5-flash"` 단일 지정 |
| API 키를 노트북에 적지 않기 | `getpass` 입력과 런타임 업로드로 분리 |
| 문항 수·번호를 코드에 고정 금지 | 문항 순회는 골드셋 파일을 읽어 동적으로 처리. 다만 `N_QUESTIONS_EXPECTED = 30` 을 두고 골드셋 길이가 다르면 중단하는 안전장치가 남아 있다 (아래 참고) |
| 파일명이 아니라 **구조**로 판별 | `BLIND01.json`으로 오든 다른 이름으로 오든 내용으로 후보를 식별 |
| 순위를 직접 기록 금지 | `total` 원점수만 저장. `rank`·`schema_version`은 쓰지 않음 |
| 다섯 후보 전부 `completed`여야 채택 | 한 문항 실패가 파일 전체를 날리므로 문항 단위 실패 격리 |
| 예산 19,800원 / 150회 순차 | 프롬프트 길이와 호출 횟수를 비용 기준으로 설계 |

설계 근거는 [`2-evaluator/평가기_코드_설명.md`](2-evaluator/평가기_코드_설명.md)에
셀 단위로 정리돼 있습니다.

> **규정과 어긋날 소지가 있던 부분** — 문항 순회 자체는 골드셋을 읽어 동적으로 하지만,
> `N_QUESTIONS_EXPECTED = 30`을 두고 `len(GOLD) != 30`이면 예외를 던지는 검사가 있습니다.
> 3일차 과제가 실제로 30문항이었고 이 값을 비우면 검사가 꺼지도록 되어 있어 실행에는
> 문제가 없었지만, "문항 수를 코드에 고정하지 않는다"는 규정 문구만 놓고 보면
> 느슨한 지점입니다. 감추기보다 적어 둡니다.

## 평가기 정확도 — 유일한 실측

개발 중 팀원이 남긴 기록입니다.

> 다른 조 테스트 해봤는데 점수가 6개 중에 4개는 운영진분들 점수랑 비슷하고
> 2개는 ±1 정도 차이납니다

운영진 연습 채점 결과가 공개된 다른 팀 답변 6개를 자체 평가기로 채점해 비교한 것으로,
4/6은 근사하고 2/6은 ±1점 차이였습니다. 운영진 채점기를 역산해 만든 것이 실제로
비슷한 값을 낸다는 확인입니다. 표본이 6개라 정밀한 일치도라기보다 **방향이 맞다는 증거**로
읽는 편이 정확합니다.

## 핵심 교훈

1. **측정하지 않은 것은 모르는 것이다.** BM25 패키지 논쟁, 임베딩 필요성, 프롬프트 규칙 위치,
   온도 방향 — 전부 직관과 측정 결과가 달랐습니다. 임베딩은 "불필요하다"고 판단했다가
   측정으로 뒤집었습니다
2. **틀린 답의 재료가 입력에 있었는지 먼저 확인한다.** 모델이 틀렸을 때 청킹을 의심했지만,
   확인해보니 필요한 문장이 청크 안에 전부 있었습니다. 확인 없이 감으로 청킹을 만졌다면
   멀쩡한 것을 망가뜨렸을 겁니다
3. **공개셋 지표는 천장에 닿으면 정보를 잃는다.** MRR 1.000은 "완벽하다"가 아니라 "이 지표로는
   더 구분할 수 없다"는 뜻입니다. 자체 검증셋을 만든 것이 가장 값어치 있는 투자였습니다
4. **채점 기준을 역산하면 우선순위가 바뀐다.** 배점을 알기 전에는 프롬프트와 모델을 만졌습니다.
   알고 나니 F1 재현율 하나에 9.4점이 걸려 있었고, 그때까지 강조하던 "간결성"이 바로 그 점수를
   깎고 있었습니다
5. **개선은 양방향으로 움직인다.** 프롬프트를 고칠 때마다 어떤 문항은 좋아지고 어떤 문항은
   나빠졌습니다. P04를 잡으면 P07이 무너지는 식이었고, 매번 백업하고 나빠지면 되돌린다는
   규율이 없었다면 최고점을 잃었을 겁니다
6. **안전한 실패와 치명적 실패를 구분한다.** 키팩트 하나 누락은 부분 점수 손실이지만,
   OOM·중국어 유출·타임아웃은 문항을 통째로 잃습니다(-3.3점). 후자를 막는 장치가 늘 우선입니다
7. **극대점을 벗어나려면 축을 바꿔야 한다.** 프롬프트를 열 번 고쳐도 88~91을 벗어나지
   못했습니다. 벗어난 계기는 그리디라는 **디코딩 방식 자체**를 의심한 것이었습니다.
   특강에서 들은 "극대는 최대가 아닐 수 있다"가 그대로 적용된 지점입니다

## 범위에 대한 밝힘

- 위 점수표는 운영진 **공개 10문항 연습 채점**이고 예선 점수가 아닙니다. 예선은 비공개
  30문항으로 따로 채점했으며 팀별 점수는 공개되지 않았습니다. 확정된 결과는 **본선 진출
  후 2위(우수상)** 이며, 발표 50 / 결과기 30 / 교차 평가 20 중 어디서 점수가 갈렸는지는
  공개되지 않아 알 수 없습니다
