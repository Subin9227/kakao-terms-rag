# 학생 평가기 코드 설명

`student_evaluator_9.ipynb` 의 셀별 구조와 각 코드가 왜 그렇게 쓰였는지 정리한다.

---

## 전체 구조

```
셀 1  설정 ─ 배점, 모델, 재시도 정책
셀 2  API 키 읽기 + 파일 업로드
셀 3  계산으로 끝나는 지표 (MRR, 키팩트 F1)   ← API 호출 0회
셀 4  골드셋 파싱 + 후보 ID 판별
셀 5  판정 기준 (프롬프트, 스키마, 점수 환산)
셀 6  Gemini REST 호출 + 재시도
셀 7  후보 한 명 채점
셀 8  전체 실행 + eval_<팀>.json 저장
셀 9  출력 형식 검증 + 다운로드
```

### 설계의 핵심 판단

**결정론적으로 잴 수 있는 것은 LLM 에 묻지 않는다.**

| 항목 | 배점 | 계산 방식 | API |
|---|---|---|---|
| 검색 순위(MRR) | 20 | `retrieved` 와 정답 조항 대조 | 0회 |
| 키팩트 F1 | 30 | 토큰 일치 계산 | 0회 |
| 판정 | 50 | Gemini 3.5 Flash | 문항당 1회 |

이 분리가 두 가지를 동시에 해결한다.

1. **비용** — 3일차 5팀 × 30문항 = 150회로 고정된다. 만약 MRR 과 F1 까지 LLM 에 물었다면
   호출당 입력이 몇 배로 늘어난다.
2. **안정성** — LLM 판정이 실행마다 흔들려도 총점의 절반(50점)은 항상 같은 값이 나온다.

### 호출 정책

```python

```

## 셀 3 — 계산으로 끝나는 지표

### 토큰화

```python
_TOKEN_RE = re.compile(r"[0-9]+|[A-Za-z]+|[가-힣]+")
```

숫자·영문·한글을 각각 따로 뽑는다. `제16조` 는 `16` 과 `조` 로 나뉘고, `SSO` 는 그대로 남는다.
약관 채점에서 숫자와 영문 표기는 그대로 비교해야 하므로 붙이지 않는다.

```python
def content_tokens(text):
    for word in _TOKEN_RE.findall(...):
        if re.fullmatch(r"[가-힣]+", word):
            for josa in _JOSA:
                if word.endswith(josa) and len(word) - len(josa) >= 2:
                    word = word[: -len(josa)]
                    break
        word = word.lower()
        if len(word) < 2 or word in _STOP:
            continue
        result.append(word)
```

**조사 제거가 정확도를 좌우한다.** `위치정보를` 과 `위치정보` 를 다른 토큰으로 두면 같은 뜻인데
일치하지 않는다.

측정 결과, 조사 제거 유무로 공식 채점기와의 오차가 크게 갈렸다.

| | 키팩트 F1 | 공식(0.7537) 대비 오차 | 30점 환산 |
|---|---|---|---|
| 조사 제거 함 | 0.7561 | **0.0024** | 22.68 |
| 조사 제거 안 함 | 0.7200 | 0.0337 | 21.60 |

세부 규칙 두 가지가 있다.

- **긴 조사부터 검사한다** — `_JOSA` 는 `으로써`, `에게서` 같은 긴 것이 앞에 온다. 짧은 것부터
  검사하면 `에게서` 가 `에` 로 잘못 잘린다. `break` 로 하나만 떼는 것도 같은 이유다.
- **`len(word) - len(josa) >= 2`** — 조사를 뗀 뒤 최소 두 글자가 남아야 한다. `이는` 같은 짧은
  단어가 한 글자로 뭉개지는 것을 막는다.

`_STOP` 은 `및`, `등`, `경우` 처럼 어느 답변에나 나와 변별력이 없는 말을 걸러 낸다. 이런 말이
남으면 아무 답이나 정답과 겹쳐 보이게 된다.

### 키팩트 F1

```python
def keyfact_f1(answer, key_facts):
    ref = Counter(token for fact in key_facts for token in content_tokens(fact))
    hyp = Counter(content_tokens(answer))
    overlap = sum((ref & hyp).values())
    precision, recall = overlap / sum(hyp.values()), overlap / sum(ref.values())
    f1 = 2 * precision * recall / (precision + recall)
```

`Counter` 의 `&` 는 다중집합 교집합이라 **같은 단어가 여러 번 나오면 적게 나온 쪽만큼만** 센다.
답변에서 한 단어를 반복해 점수를 올리는 것을 막는다.

정밀도와 재현율을 함께 보는 이유:

```
재현율만 보면 → 조항을 통째로 붙여 넣은 답이 만점
정밀도만 보면 → 핵심 단어 하나만 쓴 답이 유리
```

F1 은 **필요한 내용을 담되 군더더기가 없어야** 높다. 실제로 이 지표가 결과기 개발에서
"원문 그대로 옮기되 무관한 조항은 넣지 않는다" 는 방향을 이끌어 냈다.

### 검색 순위

```python
def parse_retrieved_item(item):
    if isinstance(item, dict):
        doc = item.get("doc") or item.get("document") or item.get("doc_name")
        article = item.get("article") if item.get("article") is not None else item.get("article_no")
        return (norm_doc(doc), art_no(article)) if doc is not None and article is not None else None
    if isinstance(item, (list, tuple)) and len(item) >= 2:
        return norm_doc(item[0]), art_no(item[1])
    return None
```

다른 팀의 결과기가 어떤 형식으로 냈든 읽어야 한다. `[["약관명", 3]]` 도, `[{"doc": ..., "article_no": 3}]`
도 받는다. **읽지 못하는 항목은 예외를 던지지 않고 `None` 을 돌려주고 건너뛴다.** 형식이 조금
다르다는 이유로 다른 팀 점수를 0 으로 만들면 안 된다.

```python
def norm_doc(text):
    return re.sub(r"\s+", "", unicodedata.normalize("NFC", str(text)))

def art_no(value):
    m = re.search(r"(\d+)", str(value))
    return int(m.group(1)) if m else None
```

- `norm_doc` — NFC 정규화 + 공백 제거. `카카오 통합 약관` 과 `카카오통합약관` 을 같게 본다.
  한글은 자모 분리 방식(NFD)으로 저장될 수 있어 정규화가 필요하다.
- `art_no` — `3` 이든 `"제3조"` 든 정수 3 으로 읽는다.

```python
def retrieval_rr(retrieved, gold_articles, cutoff=RETRIEVAL_CUTOFF):
    for rank, item in enumerate(retrieved[:cutoff], start=1):
        if parse_retrieved_item(item) in gold:
            return 1.0 / rank
    return 0.0
```

정답 조항이 **처음** 나오는 순위의 역수다. 1위 1.0, 2위 0.5, 3위 0.333, 4위 0.25, 없으면 0.
운영진 채점기와 같은 방식이다.

## 셀 5 — 판정 기준

### 프롬프트가 평가기의 성격을 결정한다

```
오직 제공된 질문, 정답 근거 조항, 정답 키팩트, 참가자 답변만 사용하십시오.
외부 지식으로 정답을 보충하거나 참가자에게 유리하게 추정하지 마십시오.
```

Gemini 가 약관을 알고 있을 수 있으므로 **주어진 자료 밖으로 나가지 못하게** 못 박는다. 이게
없으면 후보마다 다른 배경지식이 적용돼 비교가 불공정해진다.

### grounding 축의 설계

```
답변이 특정 약관명이나 조항 번호를 명시했는데 정답 gold_articles와 다르면 grounding을 감점하십시오.
잘못된 문서와 조항을 정답 근거처럼 제시한 경우 크게 감점하십시오.
단, 답변에 약관명이나 조항 번호를 아예 적지 않은 경우에는 그것만으로 감점하지 마십시오.
```

**인용을 안 한 것과 틀리게 한 것을 구분한다.** 틀린 인용은 읽는 사람을 잘못된 조항으로 보내므로
아예 안 쓴 것보다 나쁘다. 이 구분이 없으면 인용을 생략하는 쪽이 유리해져, 근거를 밝히는 좋은
답변이 손해를 본다.

### 이중 감점을 피하는 문장

```
짧다는 이유만으로 감점하지 말고 의미가 같으면 같은 사실로 인정하십시오.
```

키팩트 F1(30점)이 이미 토큰 일치를 재고 있다. 판정까지 표현 일치를 보면 **같은 것을 두 번
감점**하게 된다. 판정은 "표현이 달라도 사실이 맞는가" 를 봐야 F1 과 역할이 나뉜다.

```
답변이 비어 있거나 질문과 무관하면 각 축을 0~2점으로 평가하십시오.
```

바닥값을 명시해 두면 모델이 빈 답변에 어중간한 점수를 주는 일이 줄어든다.

```python
def build_judge_prompt(question, gold_articles, key_facts, answer, retrieved):
```

**약관 전문을 넣지 않는다.** 근거 표시(`카카오 통합 약관 제3조`)와 키팩트만 넣어 호출당 입력을

3일차 골드 파일의 필드 구성이 다를 수 있어 둔 대비책이다.

```python
def judge_score(axes):
    for name, weight in AXIS_WEIGHTS.items():
        value = axes.get(name, 0)
        value = max(0.0, min(10.0, float(value))) if isinstance(value, (int, float)) else 0.0
        total += value * weight
    return total * 10.0
```

축 점수(0~10)에 가중치를 곱해 합한 뒤 10을 곱해 0~100 으로 만든다. 스키마로 범위를 강제했지만
여기서 한 번 더 자른다. **이상값이 총점을 오염시키지 않게 하는 마지막 방어선**이다.

### thought 파트 걸러내기

**이 한 줄이 없으면 파싱이 깨진다.** Gemini 3.x 는 사고 과정을 `thought: true` 가 붙은 별도
파트로 반환할 수 있는데, 그것까지 이어 붙이면 JSON 앞에 설명문이 섞여 들어온다.

`part.get("thought") is not True` 로 쓴 이유는 `thought` 키가 아예 없는 경우(일반 응답)도
통과시켜야 하기 때문이다. `== False` 로 쓰면 키가 없는 정상 응답이 걸러진다.

### 두 가지 요청 변형

```python
payloads = [
    {..., "generationConfig": {**base_generation, "thinkingConfig": {"thinkingLevel": "low"}}},
    {..., "generationConfig": base_generation}
]
```

Gemini 3.x 부터 `temperature`, `top_p`, `top_k` 는 권장되지 않아 아예 넣지 않았고,
`thinking_budget` 대신 `thinking_level` 을 쓴다. 다만 API 버전에 따라 이 필드를 받지 않을 수
있으므로, **400 이 나면 빼고 한 번 더 시도**한다.

`thinkingLevel: "low"` 로 둔 것은 채점이 긴 추론을 요구하지 않기 때문이다. 사고 토큰도 과금
대상이라 낮추면 비용이 준다.

`maxOutputTokens: 512` 는 출력 상한이다. 이유 네 개를 한 문장씩 쓰기에 충분하고, 모델이
장황해질 때의 비용을 막는다.

### 재시도 정책

```python
except urllib.error.HTTPError as e:
    if e.code == 400:
        print(f"      [HTTP 400] payload 변형 {variant} 실패")
        break                                  # 설정 문제 → 다음 변형으로
    if attempt + 1 < MAX_RETRY:
        wait = RETRY_BACKOFF * (2 ** attempt)
        time.sleep(wait)                       # 429/500 → 기다렸다 재시도
```

**400 과 나머지를 다르게 다룬다.** 400 은 요청 형식이 잘못된 것이라 몇 번을 다시 보내도 같은
결과다. 다음 변형으로 넘어가는 게 맞다. 429(속도 제한)나 5xx(일시 장애)는 기다리면 풀리므로
지수 백오프로 재시도한다.

```python
return validate_axes(json.loads(cleaned))
```

`validate_axes` 가 축이 빠졌거나 범위를 벗어나면 예외를 던지고, 그 예외가 재시도를 유발한다.
**잘못된 점수를 조용히 받아들이지 않는다.**

모든 시도가 실패하면 `None` 을 돌려주고, 호출한 쪽에서 그 문항을 실패로 센다.

## 셀 7 — 후보 한 명 채점

### 구조 점검

```python
qid_counts = Counter(str(a["qid"]) for a in raw_answers ...)
duplicate_qids = sorted(qid for qid, count in qid_counts.items() if count > 1)
answers.setdefault(str(answer["qid"]), answer)      # 중복이면 첫 번째만 쓴다

missing_qids = sorted(gold_qids - answer_qids)
unknown_qids = sorted(answer_qids - gold_qids)
```

중복·누락·미상 qid 를 찾아 **화면에 경고로 남긴다.** `setdefault` 로 중복 중 첫 번째만 채택해
같은 문항을 두 번 채점하는 낭비를 막는다.

### status 를 정하는 기준 — 가장 중요한 부분

```python
status = "partial" if n_judge_fail > 0 else "completed"
```

여기에 `structural_problem` 을 넣으면 안 된다. 규정을 보면 이유가 분명하다.

> 다섯 후보의 `status` 가 모두 `completed` ... `partial`·`failed` 상태가 포함된 경우에는
> **해당 팀의 평가 파일 전체를 제외합니다**

즉 **BLIND 후보 중 하나가 답변을 빠뜨렸다는 이유로 `partial` 을 기록하면, 그 후보가 아니라
우리 평가 파일이 통째로 순위 산정에서 빠진다.** 20점 배점 전체를 잃는다.

정리하면 이렇다.

| 상황 | 처리 |
|---|---|
| 후보 답변이 누락됨 | 그 문항 0점, status 는 `completed` 유지 |
| 후보 답변이 비었음 | API 호출 없이 각 축 0점, `completed` 유지 |
| **우리 API 호출이 실패** | `partial` |
| **판정을 하나도 못 받음** | `failed`, `total: null` |

`status` 는 **후보의 답변 품질이 아니라 우리 평가기가 채점을 완료했는지**를 나타내는 값이다.
후보의 결함은 점수로 반영하면 된다.

### 누락 문항 처리

```python
if a is None:
    per_question.append({"qid": qid, "rr": 0.0, "keyfact_f1": 0.0, ...,
                         "judge": 0.0, "axes": None, "error": "missing_qid"})
    continue
```

`judge` 를 `None` 이 아니라 `0.0` 으로 둔 점이 중요하다. `None` 이면 아래에서 판정 평균 계산에서
제외되어 **답변을 빠뜨린 후보가 오히려 유리해진다.** 0.0 으로 두면 평균이 제대로 깎인다.

### 빈 답변은 API 를 부르지 않는다

```python
if answer_text.strip():
    axes = call_judge(prompt, api_key, usage)
    time.sleep(REQUEST_INTERVAL)
else:
    axes = {"accuracy": 0, "grounding": 0, "completeness": 0, "clarity": 0, ...}
```

빈 답변에 판정을 물어봐야 0점이 나온다. 호출을 아끼면서 결과는 같다.

### 총점 계산

```python
judge_ok = [row for row in per_question if row["judge"] is not None]
if not judge_ok:
    return {"blind_id": blind_id, "total": None, "status": "failed"}, per_question

mrr = sum(row["rr"] for row in per_question) / n              # 전체 문항으로 나눈다
keyfact = sum(row["keyfact_f1"] for row in per_question) / n  # 전체 문항으로 나눈다
judge_avg = sum(row["judge"] for row in judge_ok) / len(judge_ok)   # 성공분으로만 나눈다

total = WEIGHT_MRR * mrr + WEIGHT_KEYFACT * keyfact + WEIGHT_JUDGE * (judge_avg / 100.0)
total = max(0.0, min(100.0, total))
```

**분모가 다른 이유**가 있다. MRR 과 F1 은 우리가 항상 계산할 수 있으므로 전체 문항으로 나눈다.
판정은 우리 쪽 API 실패로 빠질 수 있는데, 그것까지 0점으로 세면 **후보의 잘못이 아닌 이유로
점수가 깎인다.** 그래서 성공한 문항만으로 평균을 낸다.

`max(0.0, min(100.0, total))` 은 규정의 "0점에서 100점 사이" 조건을 코드로 보장한다.
